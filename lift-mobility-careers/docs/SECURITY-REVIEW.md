# Security review – Lift and Mobility Careers

**Scope:** the custom plugin `lmc-core` and theme `lmc`, reviewed line by line against the 12 areas below, with an automated test for each control. **Date:** November 2026.

**What this is and isn't:** a developer security review with tests that try to break each control. It is **not** an independent penetration test, and it does not claim the site is "secure". WordPress core, the server and hosting configuration are outside it. See "Residual risks" and "Recommended before launch".

Tests: `php tools/tests/run.php` (integration, 206 checks) · `node tools/tests/e2e-employer.js` (browser, 50 checks) · `node tools/tests/e2e.js` (browser, 26 checks). All pass on a fresh local install (WordPress 7.1.4, PHP 8.3).

| # | Area | How it's implemented | Proved by (test names) |
|---|---|---|---|
| 1 | **Nonce verification** | Every front-end POST is routed through `LMC_Forms::handle_post()`; each handler checks its own nonce (`human_check()` / `wp_verify_nonce`): register, submit/edit vacancy, choose package, contact, resend verification, profile, close vacancy, close account, backlink check, alert management. Admin actions all go through `admin_post_lmc_admin` → `check_admin_referer()`. **One deliberate exception:** the anonymous job-alert sign-up form has no nonce, because it's shown on cached pages where nonces go stale. It's protected instead by a honeypot, a rate limit and double opt-in (nothing is sent until the inbox owner confirms). | "Registration without a valid nonce is refused"; e2e "Employers cannot run admin actions" |
| 2 | **Capability checks** | Admin screens/actions require `manage_options`. The employer role has **only** `read` (no `upload_files`, no editing). Employers are redirected out of wp-admin. Vacancy actions check the post author, not just login. | "Employer role has only the read capability"; e2e "Employers are kept out of wp-admin", "cannot run admin actions" |
| 3 | **Sanitisation & escaping** | Input: `sanitize_text_field`, `sanitize_textarea_field`, `sanitize_email`, `esc_url_raw`, `absint`, and `wp_kses` with a short allow-list for descriptions. Output: `esc_html`/`esc_attr`/`esc_url` throughout. **Fixed in this review:** the page `<title>` and JSON-LD structured data now escape stored values too (`esc_html`; `JSON_HEX_TAG`), so even raw data inserted by an admin or import can't break out of those tags. | "Hostile search input handled safely" ×3; "Vacancy page escapes every employer-supplied field"; "Job descriptions keep only safe formatting tags" |
| 4 | **Prepared queries** | All queries with variable input use `$wpdb->prepare()` or `$wpdb->insert/update/delete`. The only unprepared queries contain no user input (fixed table names/constants). | "Hostile search input…": SQL payloads in every search parameter; "…posts table is intact" |
| 5 | **Passwords** | WordPress core hashing (bcrypt in WP 6.8+), never stored or logged in plain text; minimum 10 characters at registration; password reset by core. Account closure requires re-entering the password. **Login throttling added:** 5 failures per IP+username (and 20 per IP) per 15 minutes. | "Passwords stored only as salted hashes"; "Login locked after 5 failed attempts"; "…even the correct password is refused while locked"; e2e "Wrong password: account not closed" |
| 6 | **Employer account isolation** | Every read/write of a vacancy checks `post_author` matches the signed-in employer: edit form (GET and POST), payment step, credit use, renewal, close, share kit. Payments, credits and dashboard queries are filtered by user ID. Usernames can't be enumerated (author archives and the public REST users list are disabled). | e2e: "B cannot open A's vacancy for editing", "…overwrite A's vacancy by tampering with the form", "…renew (or pay for)", "…reach A's payment step", "…open A's share kit", "…close A's vacancy by tampering"; "Author archives… redirected"; "REST users list hidden" |
| 7 | **File uploads** | Logo only: JPG/PNG/WebP checked by real file content (`wp_check_filetype_and_ext`), max 1MB, SVG refused (can carry scripts), explicit rights confirmation, processed by WordPress media functions. Employers cannot use the REST media API. | e2e: "PHP code disguised as .png rejected", "SVG rejected", "Files over 1MB rejected", "Logo needs the rights confirmation", "Employers cannot upload through the REST media API" |
| 8 | **Stripe webhooks** | HMAC-SHA256 `Stripe-Signature` check (v1 scheme, constant-time compare, 5-minute replay window). Amount and currency are re-checked against the local record. Card data never touches the site (Stripe-hosted Checkout). | "Valid / wrong / stale signature"; "Forged webhook returns 400"; "Amount mismatch is refused"; e2e payments run through real signed webhooks |
| 9 | **Duplicate payments & publishing** | Each payment row is claimed atomically (`UPDATE … WHERE status='pending'`), so webhook + return page can't both fulfil. **Added:** a second payment for an already-paid vacancy (e.g. two tabs) becomes a credit and the employer is told. "Now live" emails are sent once (meta flag). Refund webhooks are idempotent. | "Duplicate webhook is idempotent"; "Second payment for the same vacancy becomes a credit"; "not published twice"; "Repeated refund webhooks are idempotent"; e2e "Double payment from two tabs" |
| 10 | **Rate limiting & spam** | Honeypot and minimum fill time on all public forms; per-connection limits: registration 5/hour, contact 5/hour, job alerts 10/hour, login as above. Limits use a **salted hash** of the IP held for ≤1 hour; IPs are never stored by the plugin. First adverts and flagged wording are held for human approval. | "Honeypot field blocks bots"; "Forms submitted faster than a human could are refused"; "Registration rate limit"; "Contact form rate limit"; content-flag tests |
| 11 | **Unauthorised job editing** | As 6, plus status changes only through controlled code paths: employers can't publish without payment/credit and approval, and edits never change status (except flagged content, which sends it back for review). | e2e isolation tests; "First-time employer → held for approval" |
| 12 | **Unsubscribe & job-alert links** | Marketing unsubscribe links are HMAC-signed per address; one-click (RFC 8058) supported. Job-alert manage/unsubscribe links use a random 40-character token per subscriber; unsubscribe deletes the data. "Filled?" answer links and email verification links are signed or hashed. A `Referrer-Policy` header stops tokens in URLs leaking to other sites. | "Tampered unsubscribe link does nothing"; "Genuine one-click unsubscribe works"; "Guessed job-alert management token rejected"; "'Filled?' answer links are signed"; "Email verification links cannot be guessed"; "Unsubscribe link deletes the subscription and email" |

## Also checked
- **Security headers:** `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (test: "Security headers sent").
- **Secrets:** Stripe, SMTP and Google keys can live in `wp-config.php` constants, kept out of the database. Password fields are never echoed back in admin.
- **Admin messages:** admin notice text from the query string is escaped (text only).
- **Pre-launch lock:** real card payments are impossible until the launch checklist passes (Stripe forced to test mode).

## Residual risks (known, accepted or to be handled by hosting)
1. **Anonymous analytics counters** (`/wp-json/lmc/v1/hit`) can be inflated by someone scripting requests. They only hold counts, never personal data. Bots are filtered by user agent.
2. **Distributed password guessing** across many IPs isn't fully stopped by per-IP throttling. Mitigation: strong passwords, plus 2FA on admin accounts (e.g. Wordfence free).
3. **Uploads folder:** the host must not execute PHP in `wp-content/uploads` (standard on managed WordPress hosting; check).
4. **WordPress core and server** security depend on updates and hosting – keep auto-updates on.
5. **Admins** can enter HTML (WordPress `unfiltered_html`), which is normal for site owners. Keep admin accounts few, with 2FA.

## Recommended before launch (low or no cost)
- Run a free external scan once the site is on its domain (e.g. WPScan, Patchstack free, Mozilla Observatory for headers).
- Enable 2FA for the admin account and keep only one admin.
- Optional: a short professional WordPress security review if budget allows once revenue starts.
